VANGUARD — TESTS DANS LA MACHINE VIRTUELLE WINDOWS
==================================================

Double-clic sur TESTER-VANGUARD.bat : un menu propose

  1  Test complet automatique, sans question (5 à 15 min, conseillé)
  2  Test complet avec questions (fenêtres UAC, mot de passe, écran)
  3  Ouvrir Vanguard, pour essayer à la main
  4  Voir le dernier rapport
  5  Ouvrir le dossier des résultats
  6  Tester seul chaque nouvelle version (activer / désactiver)
  7  Lancer les scripts déposés depuis Linux (accepter / refuser)

Avec le choix 6 activé, chaque nouvelle version déposée depuis Linux est testée
toute seule, en arrière-plan, sans rien ouvrir à l'écran ; une notification
prévient à la fin. Rien à faire de ton côté.

Avec le choix 7 accepté, un script PowerShell posé dans a-lancer\ depuis Linux
(outils/vm-script.sh) est lancé tout seul dans les 5 minutes, dans ce compte,
sans droits administrateur ; sa sortie va dans resultats\. Le dossier partagé
s'écrit depuis Linux : à n'accepter que dans une machine virtuelle de test.
L'accord est gardé dans ce Windows, pas dans le dossier partagé.

ESSAIS SANS CLIC (file d'essais)
--------------------------------
Une seule fois : sur Linux, outils/vm-tester.sh --installer ; ici, double-clic
sur INSTALLER-ESSAIS-AUTO.bat, « Oui » à la fenêtre UAC, puis « o ». Il
affiche un CODE DE VÉRIFICATION : sur Linux, vm-tester.sh montre le sien ;
n'y répondre « o » que s'il est identique. Une tâche planifiée, Vanguard-File-Essais, tourne
ensuite toute seule tant que la session est ouverte. Depuis Linux,
outils/vm-tester.sh dépose un essai dans file-essais\<id>\ : la tâche vérifie
l'empreinte de chaque fichier, lance test.ps1 (automatique, en administrateur),
puis essaie les menus de Vanguard dans une vraie console (conhost, et Windows
Terminal s'il est là, en français et en anglais), et écrit fini.txt. Plus
aucun double-clic ni UAC par essai.

Pendant ces essais, des fenêtres de Vanguard s'ouvrent environ une minute :
ne pas taper dedans (les vraies touches se mêleraient aux essais).
Un seul test à la fois : la tâche attend tant qu'une passe du menu tourne
(témoin resultats\.test-en-cours.txt), et le choix 6 attend la fin d'un essai.
Le menu ne peut pas arrêter un essai de la file (il tourne en administrateur) :
il le dit et attend ; DESINSTALLER-ESSAIS-AUTO.bat l'arrête. Un essai coupé en
route (VM redémarrée, session fermée, réinstallation) finit en erreur au tour
suivant, et la file repart.

Essais de console : un OK exige le texte vu à l'écran et l'effet mesuré. Sous
Windows Terminal, un écran illisible est « sauté » avec la raison ; sous
conhost, c'est un problème (Vanguard bloqué ou arrêté). Une partie demandée
sans un seul OK n'est jamais un essai réussi.

RÉINSTALLER UNE FOIS (24 oct. 2026) : depuis la signature des travaux, le
surveillant d'avant ne reçoit plus rien. Sur Linux outils/vm-tester.sh
--installer, puis ici INSTALLER-ESSAIS-AUTO.bat (double-clic, UAC, « o »), et
comparer le code. Jusque-là, vm-tester.sh refuse de déposer, et le dit.

SÉCURITÉ. Ce qui est déposé dans file-essais s'exécute EN ADMINISTRATEUR dans
cette VM, sans clic. Le dossier partagé s'écrit depuis Linux, mais aussi depuis
cette VM, par n'importe quel compte : la tâche ne fait donc qu'un travail signé
(HMAC-SHA256 de travail.txt, empreintes des fichiers comprises) par le secret
tiré à l'installation. Ce secret vit ici dans secret.bin, que seuls les
administrateurs lisent, et sur Linux hors du partage ; il n'a traversé le
partage que chiffré pour la seule clé de Linux, et le code de vérification
prouve que personne ne l'a échangé en route. Un travail déjà fait n'est jamais
refait ; fini.txt porte la signature du surveillant, et Linux ne croit que
celui-là. Tout programme du compte Linux, qui lit ce secret, peut encore
devenir administrateur de la VM. À n'installer que
dans la VM de test, jamais sur un vrai PC : l'installateur et la tâche ne font
rien sans \\host.lan\Data. L'empreinte SHA-256 est vérifiée sur la copie
locale, juste avant le lancement. Seuls les fichiers
nommés dans travail.txt (vanguard.exe, test.ps1, essais-console.ps1, le
lanceur de la clé) sont copiés. Un lien symbolique de Linux, Samba le suit
sans que Windows le voie : outils/vm-tester.sh refuse d'en déposer.
Le surveillant et les travaux vivent dans %ProgramData%\Vanguard-File-Essais
(créé par l'installation, modifiable seulement par un administrateur ; un
dossier déjà là sans ces droits est écarté, et la tâche ne lance rien si ses
droits ont changé). Tout ce qui tourne en administrateur est lancé de là
(test.ps1 -SurPlace), jamais d'un dossier où un programme sans droits écrit ;
Windows Terminal est pris dans le dossier de son paquet, pas par le PATH. Le
surveillant ne se met jamais à jour lui-même : réinstaller (une UAC) le met à
jour. Rien n'est envoyé ailleurs.

Pour tout retirer : double-clic sur DESINSTALLER-ESSAIS-AUTO.bat (une UAC).
Les résultats restent.

CE QU'IL Y A ICI
----------------
programme\    vanguard.exe et les scripts de test. Remplacé à chaque mise à
              jour de Vanguard (outils/deployer.sh, côté Linux) : ne rien y
              mettre.
a-lancer\     les scripts déposés depuis Linux qui attendent (choix 7).
file-essais\  les essais sans clic : un dossier par essai (travail.txt,
              fini.txt, resultats\ avec le rapport et les écrans de la
              console), historique.txt, battement.txt (la tâche est en vie).
              Gardés 14 jours.
resultats\    une passe par dossier, nommée AAAA-MM-JJ_HH-MM-SS_vX.Y.Z (date et
              version testée), avec son rapport (rapport-test.html) et la
              sortie de chaque commande.
resultats\historique.txt       une ligne par passe : date, version, bilan.
resultats\dernier-rapport.html le rapport de la dernière passe.

Les résultats restent d'une version à l'autre : rien n'est effacé.
Si l'Explorateur ne montre pas un fichier nouveau : touche F5.
